Metrics and Endpoints Reference#

Ports, HTTP endpoints and Prometheus metrics exposed by the local stack and Heartbeat services. For how the pieces connect, see the architecture overview.

Local ports (kind)#

The kind cluster (infra/kind/cluster.yaml) maps fixed NodePorts to these ports on 127.0.0.1 only.

Service Host port(s) Notes
DB collector 8082 Heartbeat service
Prometheus 9090 15s scrape interval
Grafana 3001 Local login admin/admin, anonymous viewer enabled. Local only.
Alertmanager 9093
OpenTelemetry Collector 4317 (OTLP gRPC), 4318 (OTLP HTTP) full profile. Heartbeat's own logs use a third port, 4319, in-cluster only
Loki none In-cluster only (loki:3100); query it through Grafana, or kubectl port-forward svc/loki 3100
Tempo none In-cluster only (tempo:3200, OTLP on tempo:4318); query it through Grafana, or kubectl port-forward svc/tempo 3200. full profile
SQL Server (dev target only) 127.0.0.1:11433 Loopback-bound Docker container; see the local development guide

Inside the cluster every component keeps its Compose-era name and port (prometheus:9090, alertmanager:9093, loki:3100, otel-collector:4318, db-collector:8082), beside the API (api:8081), its PostgreSQL (postgresql:5432) and Valkey (valkey:6379). NetworkPolicies admit only the components that use each one (network access): a pod of your own times out on them, so reach them through the host ports above, Grafana or kubectl port-forward; the API has no host port.

DB collector (:8082)#

Endpoint Auth Behavior

GET /healthz (alias /healthcheck) none Liveness only; 200 while the process serves HTTP

Target health is heartbeat_collector_target_up and the target states below. The body is only {"status":"ready"} or {"status":"not_ready"}; the reasons are in GET /admin/config.

last_reload_err, runtime_diverged, rollback_err Why the last reload was rejected or failed; set until the next successful reload. Monitoring sees it as heartbeat_collector_config_last_reload_successful 0

curl -s -H "Authorization: Bearer local-admin-token" localhost:8082/admin/config | jq .readiness   # kind

Admin authentication. Both admin endpoints go through one check: exactly one Authorization: Bearer <token> header (scheme case-insensitive), whose SHA-256 digest is compared in constant time with the digest of HEARTBEAT_ADMIN_TOKEN computed at startup, so neither the token nor its length leaks through timing. A missing or wrong token gets 401 with a WWW-Authenticate: Bearer challenge before the method is checked (an authenticated wrong method gets 405). Admin responses are Cache-Control: no-store. With no token configured, both endpoints always answer 401.

Network access. In Kubernetes the db-collector NetworkPolicy admits only Prometheus and the configured operator peers to port 8082 (what the chart deploys). Operators reach the admin endpoints with kubectl -n heartbeat port-forward pod/db-collector-0 8082, which NetworkPolicy does not apply to, or from a listed peer such as a VPN range.

API (:8081)#

The control plane (ADR 0013). The chart deploys it as Deployment/api behind Service/api (ClusterIP); reach it with kubectl -n heartbeat port-forward svc/api 8081. Its contract is apps/api/openapi.yaml; /metrics is served beside it.

GET /healthz none Liveness only; 200 ok while the process serves HTTP. It checks no dependency, so a PostgreSQL or Redis outage never restarts the pod
GET /readyz none 200 when every readiness check passes, 503 otherwise. Each passes again on its own once its dependency is back. The body is only {"status":"ready"} or {"status":"not_ready"}; the failing checks and their errors (schema not migrated, a refused connection, a failed login, never a password) are logged when the status changes

POST /api/v1/probe-definitions/{id}/versions session, admin; Origin Change a custom definition: 201 with the next version

GET /api/v1/users, GET /api/v1/users/{id} session, admin The users, by email (?status=active or disabled), or one

PUT, DELETE /api/v1/users/{id}/roles/{role} session, admin; Origin Grant or revoke a role

On SIGTERM or SIGINT the API answers GET /readyz with 503 and keeps serving for HEARTBEAT_API_SHUTDOWN_DELAY (5s), while its Service stops sending it requests; then it stops accepting connections and its audit drainer, waits up to 10s for the requests in flight, closes the rest, then closes its PostgreSQL and Redis connections. An audit export in flight is abandoned, and its records are sent again by another replica or the next one; records the Collector already accepted are still deleted, within 5s.

Logging in and sessions#

Local users log in with their email and password and get a cookie session (ADR 0013 §7–8). The first admin comes from api users create-admin; admins make the other users and give them roles through the API (users and roles).

Who may call what. Every operation in openapi.yaml declares it with security: [] for one anyone may call, or the session scheme with the least role it needs. Roles rank viewer (reads; wallboards) < operator (changes inventory, sources, targets and probes) < admin (everything, users and roles included); a user may call what any of their roles allows. The API reads each operation's rule from the spec at startup and refuses to start if one declares none, so no operation is served on a default.

Before each operation, in this order: the response gets an X-Request-Id (a UUID, the request_id of any audit record the request writes); a body over 1 MiB is refused; POST, PUT, PATCH and DELETE need one Origin header equal to HEARTBEAT_API_SITE_ORIGIN (403 otherwise; browsers send it with every such request, so a page on another site cannot make one with the user's cookie); then, unless the operation is public, the session cookie must name a live session (401, and the cookie is cleared) whose user is active and has the role (403). The user and their roles are read on every request: disabling a user or changing their roles applies to their next request. Only then are the path and query parameters read (400 for a malformed one), so a request without a session gets 401 whatever its parameters, and then the body: a JSON object whose members are all listed by the operation's schema, spelt exactly, or 400 naming the first that is not. A member that cannot be set is refused, never ignored.

Logging in. POST /api/v1/session with {"email": "...", "password": "..."}:

Status When
201 Logged in. The body is the session (id, user with id, email, display_name, roles, created_at, expires_at); Set-Cookie holds the session
400 Not JSON, an email that is not an address, or a password that is empty, over 1,024 bytes or not UTF-8. Not counted as a failure
401 Wrong password, unknown email, disabled user, a user without a password: the same wrong email or password for all, after the same work (an unknown email is checked against a decoy hash), so neither the answer nor its time tells which accounts exist
403 Origin missing or not the site
429 Too many failures: 10 for the account, or 50 from the client address (an IPv6 address counts as its /64), within 15 minutes of the first. Refused without checking the password, even the right one, until the window ends; Retry-After says in how many seconds. A login counts before its password is checked, so concurrent attempts cannot pass the limits. A success clears the account's count, not the address's

A hash made with older argon2id parameters is replaced with one made with the current ones at a successful login.

The cookie is __Host-heartbeat_session: HttpOnly, Secure, SameSite=Lax, Path=/, no Domain, kept until the session's absolute end. Its value is 256 random bits, base64url; Redis keeps only its SHA-256, as the key of the session (user, client address, created and last-seen times), which expires by itself at the earlier of 8 hours without a request and 7 days after login (HEARTBEAT_API_SESSION_IDLE_TIMEOUT, _MAX_AGE). The session's id in the body and in audit records is another random UUID: it identifies the session but cannot log in. A browser keeps a Secure cookie only from HTTPS, or from localhost.

Audit. A login, a logout and a failed login each write an audit record of entity type session (audit delivery): login with the session in after and the user as actor, logout with it in before, login_failed with the email tried, the user's ID when it exists and the reason (wrong_password, unknown_email, disabled, no_password, unreadable_hash, changed_meanwhile) in after, and the client's address as actor (client). The client is never told the reason. No record holds a password, a hash, the token or its SHA-256. A login is written in one transaction with its record and the user's last_login_at; the session is created in Redis before it commits and deleted again if the commit fails. A logout whose session cannot be deleted fails and records nothing.

On kind, through a port-forward, with the admin made by api users create-admin; the password comes from a file, never the command line:

kubectl --context kind-heartbeat -n heartbeat port-forward svc/api 8081 &
jq -n --rawfile p admin-password '{email: "admin@example.com", password: ($p | rtrimstr("\n"))}' |
  curl -sS -c cookies -H 'Origin: http://localhost:8081' -H 'Content-Type: application/json' \
    --data @- localhost:8081/api/v1/session
curl -sS -b cookies localhost:8081/api/v1/session                     # the session and its user
curl -sS -b cookies -X DELETE -H 'Origin: http://localhost:8081' localhost:8081/api/v1/session

Inventory#

Environments, their applications, and the applications' components (data model), under /api/v1. Viewers read; operators create, change and delete. The fields and their limits are in openapi.yaml.

Path Operations Notes
/api/v1/environments GET (?status=), POST Listed whole, by name: an organisation has few
/api/v1/environments/{id} GET, PATCH, DELETE slug cannot change
/api/v1/applications GET (?environment_id=, ?status=, paged), POST environment_id in the body
/api/v1/applications/{id} GET, PATCH, DELETE environment_id cannot change
/api/v1/components GET (?application_id=, paged), POST application_id in the body
/api/v1/components/{id} GET, PATCH, DELETE application_id cannot change

One ownership path. An application belongs to the environment it was created in, and a component to its application, for good: the same system in another environment is another application. A component's environment_id is read through its application; it is not stored and cannot be set. A PATCH or POST naming an owner it cannot set is 400.

Environment slugs are what the collectors call the environment: each collector's environment, the environment label of the probe metrics and the logs' deployment.environment.name (ADR 0017 §2). Lower-case letters, digits and hyphens, 1 to 63, starting and ending with a letter or a digit (prod, local-dev); unique, and fixed once created.

Pages. Lists of applications and components hold limit items (1 to 200, 50 by default), by name then ID, and a next_cursor while more follow; pass it as cursor for the next page. The cursor marks a position, not an offset, so an item added or removed meanwhile neither repeats nor skips another.

Changes. POST answers 201 with the entity and its Location. PATCH changes the members the body holds and keeps the others; labels are replaced whole. A PATCH that changes nothing answers 200 with the entity as it is, keeps updated_at and writes no audit record. Disable an environment or an application (status: disabled) to retire it; disabling an environment leaves its applications' status as it is.

Status When
400 A field out of its limits or format, an unknown member, a malformed ID, limit or cursor
404 No entity has the ID
409 Another environment has the slug, the environment has an application of that name, or the application a component of that name and type; or a DELETE while other rows refer to the entity: the detail names them (an environment's applications, database targets or investigations; an application's components, telemetry sources, investigations, alert policies, notification routes, alert events or reports), and nothing is deleted. A deleted application's adaptive baselines go with it
422 The body's environment_id or application_id names nothing

Audit. Each change writes one record in its transaction: entity type environment, application or application_component, action create, update or delete, the entity as the API shows it in before and after, the user as actor. A refused change records nothing.

Telemetry sources#

Which telemetry is an application's own (ADR 0017), under /api/v1/telemetry-sources: GET (?application_id=, ?environment_id=, ?source_type=, ?status=, paged by application_name) and POST; GET, PATCH and DELETE on /{id}. Viewers read; operators register, change and delete. Each change is audited as entity type telemetry_source.

{"application_id": "<id>", "source_type": "outsystems", "ingest_mode": "agentless",
 "config": {"application_name": "Claims"}}
  • Owner. A source belongs to the application it was registered for, for good; its environment_id is the application's, read through it. Neither the application nor the source type can change.
  • config is checked against its type's JSON Schema, packages/config-schema/src/telemetry-sources. For outsystems, application_name is the OutSystems Application_Name, the service.name of its logs, matched exactly. The schemas are closed and hold no credential: a schema names one only as a reference (env/, kv/ or secret/, format credential-ref), and a test fails on a schema that breaks this. ingest_mode is agentless (OutSystems 11, read from the logging database) or otlp (OutSystems Cloud and ODC).
  • One name, one application. Within an environment, an application_name belongs to one application (409 otherwise), and an application has one source per type, ingest mode and name.
  • Observation. Each source says whether the DB collector observes it. The API reads the collector's redacted GET /admin/config with the collector's admin token, at most every 15 seconds, within 2 seconds.
observation.status When
observed An enabled outsystems_logs collector extracts a target whose environment is the source's environment's slug (the collector's environment unless the target sets its own; only the targets target_names selects). collectors lists them
not_observed The collector answered, and none does. A source may be registered before its extraction is set up; nothing is refused
unknown The collector could not be asked: no URL set, no answer, a refused token. detail says which; the request itself still succeeds
not_applicable An otlp source, which sends its telemetry itself

The observation is not stored or audited: it is read with the source.

Database targets#

The databases the collector monitors [4.5], under /api/v1/database-targets (GET with ?environment_id=, ?status= and pages like applications'; POST; GET, PATCH and DELETE on /{id}). Viewers read; operators create, change and delete. A target belongs to the environment it was created in, for good, as an application does.

Field Rule
name The target label of its metrics, beside the environment's: a slug like an environment's (finance-prod), unique in its environment, fixed once created. The collector refuses two targets of one environment with one name, since they would write the same series
engine sqlserver, the default; fixed
host Checked as the collector checks it: a host name, an IPv4 address or a bare IPv6 address, with no port, brackets, credentials or path; at most 253 characters; stored in lower case, and an IPv6 address in its canonical form
port 1 to 65535; 1433 when left out
database_name Empty for the login's default database; at most 128 characters; compared without regard to case, as SQL Server does by default
credential_ref kv/, secret/ or env/ and a name of lower-case letters, digits and -, at most 200. The collector reads username:password from the key HEARTBEAT_CREDENTIAL_<REF> of its credentials Secret (credential resolution): env/finance-prod is HEARTBEAT_CREDENTIAL_ENV_FINANCE_PROD. Stricter than the collector's own rule, which the API runs too, so the API stores no reference the collector refuses, and each key has one spelling: env/Finance.Prod, which the collector would read from the same key, is refused rather than passing for another reference. A value shaped like a credential is refused, and the problem does not repeat it
status, labels As for applications

The environment, engine and host, port and database together are unique: a second target for the same database in one environment is 409.

Credentials and reachability. The API stores the reference only and never connects to a target (ADR 0013 §1): it has no credential to connect with. The credential reaches the collector on its own path, a Secret key (database targets guide). Whether a target is reachable is the collector's to report, once a probe assignment renders it into a collector: its heartbeat_collector_target_up, and its state and driver error in GET /admin/config (readiness.collectors[].targets[]). A change to a target's host, port, database or credential reference sends its approved assignments back to draft, each with an audit record of its own: an approval covers the target as it was, so the collector never logs in to a server, or with a credential, that nobody approved. A change of status or labels keeps them: a disabled target is not rendered, and enabled again it runs as approved.

Deletes. A target's probe assignments would be deleted with it, so a delete is refused (409) while it has any: disable it instead (status: disabled).

Audit. Each change writes one record in its transaction: entity type database_target, action create, update or delete, the target as the API shows it, credential reference included, in before and after.

curl -sS -b cookies -H 'Origin: http://localhost:8081' -H 'Content-Type: application/json' \
  --data '{"environment_id": "<id>", "name": "finance-prod", "host": "sql01.finance.internal", "credential_ref": "env/finance-prod"}' \
  localhost:8081/api/v1/database-targets

Probe definitions#

A probe definition is what a probe assignment runs against a database target [4.5]. It is versioned: each version is immutable once stored, except whether its definition is enabled, so an assignment that pins a version keeps what was approved, and nothing is ever deleted.

  • Built-in definitions are the db-collector's SQL Server catalog, one per probe, version 1, seeded by migration 0004 with no query: the collector runs its own. They are read-only (409) and change only with the collector; a test fails when the seed and the catalog differ. The OutSystems log types are not definitions: their collectors stay in YAML (ADR 0017).
  • Custom definitions replace the query of the built-in they overrides, as a query_template does: that built-in's metric descriptors decode the rows, so the query returns the same columns in the same units, and the definition takes its category. Only admins create and change them, since their SQL runs on monitored databases; review each one with the probe review checklist.

POST /api/v1/probe-definitions takes engine (sqlserver), name (custom_ and then lower-case snake_case, at most 63 characters: no built-in's name starts with custom_, so a probe the collector adds later never clashes with one), overrides, query_template and, optionally, description (at most 1,000 characters), default_interval_seconds (5 to 3,600; 30, the collector's default, when left out) and timeout_ms (1 to 25,000; left out, the collector's default, half the interval and at most 10 s). engine, name and overrides are set once: every version overrides the same built-in. POST /api/v1/probe-definitions/{id}/versions takes the rest: a version is the whole content, so a field left out takes its default, not the previous version's value.

The query must be one read-only SELECT, checked by the same function the db-collector runs when it loads integrations.yaml (config.ValidateReadOnlySelect), so the API stores no query the collector would refuse; the problem's detail says why, without quoting the query. As in the collector, the check is a safety net and the collector's read-only login is the control. It does not check which columns the query returns.

Status When
201 Created, or a version added; Location is the new version's URL
200 From POST .../versions: the content equals the version the path names, so nothing was added
400 A field out of bounds or an unknown member, an explicit 0 for default_interval_seconds or timeout_ms, an overrides that names no enabled built-in of the engine, a query that is not one read-only SELECT, or a malformed ID
404 No version has the ID
409 The name is taken; the definition is built-in, or disabled (enable it before adding a version); or the version the path names is no longer the latest, because someone added one since it was read: read the latest and change that, so no change is lost

Changes to one definition take turns: each locks the definition until it commits. Audit. Every change writes an audit record of entity type probe_definition in the same transaction (audit delivery), with the admin as actor and the versions in full, query included: create with version 1 in after; update for a new version, whose ID is the record's entity_id, with the version it follows in before; disable and enable with the version the request named.

curl -sS -b cookies localhost:8081/api/v1/probe-definitions | jq '.items[] | {id, name, version, builtin}'
jq -n '{engine: "sqlserver", name: "custom_waits_lean", overrides: "waits",
        description: "Waits over 1 ms only",
        query_template: "SELECT wait_type, wait_time_ms FROM sys.dm_os_wait_stats WHERE wait_time_ms > 1"}' |
  curl -sS -b cookies -H 'Origin: http://localhost:8081' -H 'Content-Type: application/json' \
    --data @- localhost:8081/api/v1/probe-definitions

Probe assignments#

A probe assignment runs one probe definition version against one database target, at an interval [4.5] (ADR 0014), under /api/v1/probe-assignments (GET with ?database_target_id=, ?state= and pages; POST; GET, PATCH and DELETE on /{id}; POST /{id}/approve and POST /{id}/reject). Viewers read; operators create, change and delete; admins approve and reject.

The API never writes cluster state. It renders every approved, enabled assignment of an active target and an enabled definition into one values file, the chart's managedCollectors: one sqlserver collector per target, with the ID api-<target id>-<interval>s, which the assignment shows as collector_id. A built-in definition is listed by name; a custom one by the name of the probe it overrides, with its query in full, for review. The file is deterministic (sorted, no timestamps), and checked with the integrations schema and the collector's loader before it leaves the API. GET /api/v1/probe-assignments/rendered serves it to operators as application/yaml; on kind, make kind-assignments deploys it. The pull request to heartbeat-deploy that carries it in production waits for that repository [18].

State Meaning
draft Created or changed, not yet approved; not rendered
approved Approved by an admin; rendered
applied The collector runs it as rendered: its collector is in GET /admin/config, enabled at the interval, with the target as rendered and the probe with the same query, timeout and row limit. The API checks every 30 s and moves approved to applied only
rejected Refused by an admin, with the reason in state_detail; not rendered. Change it, or approve it after all, to try again
proposed, failed With the pull request output: in an open pull request, or refused by the config repository's checks or by the collector

Users and roles#

What each role may do. Each user has one or more roles; a role allows what the roles below it do, and a user may call what any of their roles allows.

Role May For
viewer Read everything the API serves: inventory, telemetry sources, database targets, probes and their assignments. Show their own session, log out, change their own password. Nothing else changes Wallboards and people who only look. A wallboard logs in as a user of its own with only viewer, so its session, left on a shared screen, can change nothing
operator What a viewer may, and create, change and delete inventory, telemetry sources, database targets and probe assignments The SREs who onboard applications and databases
admin What an operator may, and manage custom probe definitions, whose SQL runs on monitored databases (below), and users and roles Whoever runs Heartbeat. The first comes from api users create-admin

Each operation's least role is its security in openapi.yaml, and the roles are rows in roles (migrations 0002 and 0003).

Managing users takes admin. Users are never deleted: disable them.

  • Create: POST /api/v1/users with {"email", "display_name", "password", "roles": [...]}. display_name defaults to the email's local part, and at least one role is needed. The email is stored in lower case and must not belong to another user in any case (409). The password is 15 characters to 1,024 bytes and is stored only as its argon2id hash. It appears in no response, log or audit record.
  • Change: PATCH /api/v1/users/{id} with any of email, display_name and status.
    • Disabling a user ends every session they have at once, and refuses their logins until they are active again.
    • A body that changes nothing changes and audits nothing.
  • Set a password: PUT /api/v1/users/{id}/password with {"password"}, as for a user who has forgotten theirs. Every session of theirs ends.
  • Roles: PUT and DELETE /api/v1/users/{id}/roles/{role} grant and revoke one. Granting a role the user has, or revoking one they lack, changes nothing. A user keeps at least one role: revoking their only one is refused (409); disable them instead. The user's next request has the new roles; their sessions go on.
  • The last active admin can be neither disabled nor stripped of admin (409). The check and the change hold a lock on the admin role, so two admins cannot disable each other at the same moment and leave none.

A password change and its sessions' end are one step. The change locks the user's row and ends their sessions in Redis before it commits; if the sessions cannot end, nothing changes. A login records itself only while the user is active and still has the hash it checked. So a login that checked the old password just before the change gets 401 instead of a session, and its audit record gives the reason changed_meanwhile.

Your own password: PUT /api/v1/account/password with {"current_password", "new_password"} takes any role.

Counters. Waits, throughput and file I/O are cumulative in SQL Server (the Batch Requests/sec and Transactions/sec performance counters are totals despite their names), so they are exported as counters with the value SQL Server reports. Query them with rate() or increase(), never raw. A SQL Server restart, a failover, or DBCC SQLPERF('sys.dm_os_wait_stats', CLEAR) lowers the value; rate() and increase() treat that drop as a counter reset, so rates stay correct (the increase between the last scrape before the reset and the reset itself is lost). A failed probe, a target backing off or a collector restart leaves a gap but no reset: the counter resumes at SQL Server's value. A wait type appears when its wait time first becomes non-zero, so its first increase after SQL Server starts is not counted.

The waits probe leaves out benign idle waits (system tasks sleeping, queues waiting for work, timers such as SLEEP_TASK, LAZYWRITER_SLEEP or XE_TIMER_EVENT), which grow by about a second per second on an idle server and would dominate top-N panels. The list follows Paul Randal's widely used wait statistics query and lives in catalog.go.

CPU. SQL Server's scheduler monitor writes one record a minute with the host's CPU split over that minute: the SQL Server process, other processes, and idle. The cpu probe reads only the newest record, so both ratios (0–1, of all the CPUs SQL Server sees) change once a minute whatever the scrape interval, and lag the real load by up to a minute; idle is 1 - their sum. SQL Server on Linux reports no idle time (always 0, measured on 2019 and 2022), so heartbeat_sqlserver_cpu_other_process_ratio is exported on Windows only (the probe reads the platform from @@VERSION). Nothing is exported in the first minute after SQL Server starts, nor while the newest record is 3 minutes old or more, so a scheduler monitor that stops writing shows as a gap rather than a frozen value.

Buffer cache. Page life expectancy (seconds) and the buffer cache hit ratio (0–1) come from the server-wide Buffer Manager performance counters, on default and named instances alike. There is no fixed good page life expectancy; compare a target with its own baseline. The hit ratio stays close to 1 on most servers even under memory pressure, so read it together with page life expectancy and file reads. Both are server-wide: on a server with several NUMA nodes, a page life expectancy drop on one node can hide in the Buffer Manager value. Per-node values (Buffer Node counters) are planned (TODO §11.2).

File I/O. file_io exports six counters per database file, labelled like the storage probe's file size: read and write operations, bytes read and written, and I/O stall seconds (the time SQL Server waited for reads or writes to complete). Average latency per operation is the stall rate over the operation rate, e.g. rate(heartbeat_sqlserver_database_file_read_stall_seconds_total[5m]) / (rate(heartbeat_sqlserver_database_file_reads_total[5m]) > 0), where > 0 leaves no value instead of dividing by zero for an idle file. The counters restart at 0 when SQL Server restarts or a database comes back online, which rate() treats as a reset. A stock instance has about 10 files (60 series); budget 6 series per file, so a server with 100 databases and two files each exports about 1,200. storage and file_io label a database whose name SQL Server does not return (the login lacks VIEW ANY DATABASE, or the database was dropped during the query) database_id:<id>.

A target, identified by environment and name, may be enabled in only one sqlserver collector: configuration that lists it twice is rejected, because both collectors would write the same series and double the load on the database. The exporter also keeps each counter series to a single writer and logs any other write instead of applying it.

Each catalog metric descriptor sets the type and the unit scale applied to the query column (milliseconds to seconds, KB or 8 KB pages to bytes). A collector that overrides a probe's query_template must return the same columns in the same units.

A failed probe clears its series instead of exporting stale values, and a removed collector's series are deleted. A failing probe fails only itself. For example, storage and file_io read sys.master_files, which a long RESTORE or schema change can lock until the probe times out. While the target's other probes succeed, the target is degraded, stays up (heartbeat_collector_target_up 1) and keeps collecting, and the failing probe (heartbeat_collector_probe_up 0) backs off on its own, with the same schedule as a target (the next cycle, then doubling up to 5m, with jitter) and its series cleared until it succeeds again. A target fails, and backs off as a whole, only when every probe that ran failed, as when its database is unreachable or its login is refused; the probes' own backoffs are then forgotten. When every probe of a target is backing off on its own, they all run. While a target backs off none of its probes run and all its probe series are cleared, so they leave a gap instead of a frozen value; only the heartbeat_collector_target_* and heartbeat_collector_probe_up series stay.

A probe that returns no rows exports no series: heartbeat_sqlserver_blocked_requests is absent, not 0, while nothing is blocked. Queries that need a zero fall back to targets whose blocking probe succeeded (heartbeat_collector_probe_up{probe="blocking"} == 1), as the dashboard's Blocked Requests panel does, so neither an unreachable target nor a failing blocking probe reads as 0. The catalog lives in catalog.go.

OutSystems log extraction#

outsystems_logs collectors (configuration) report these on the same /metrics, labelled collector, environment, target and log_type. Their targets also get the self-observability series above, with the log type as the probe label: one probe execution reads, delivers and acknowledges up to 10 batches.

The recount. Every admin or operator change writes an audit record to the audit_outbox table in its own transaction; a drainer in each API replica sends the oldest records to the OTel Collector and deletes them once it accepts them (ADR 0016). So far the audited changes are api users create-admin (configuration), logins, logouts and failed logins (sessions), inventory changes (inventory), telemetry sources (telemetry sources), and users and their roles (users and roles). The drainer claims up to 100 of the oldest rows at a time with FOR UPDATE SKIP LOCKED, so replicas never send the same rows at once, and sends them with the OTLP client the db-collector uses (client="audit" in heartbeat_otlp_export_attempts_total): one export, retried for up to 30s, holds a round's rows. It goes on at once while it finds full batches, polls every 2s once the outbox is empty, and backs off from 1s to 30s while the Collector fails, logging audit: delivery failed once, then every minute, and audit: delivery resumed. A request the Collector accepts while refusing some of its records (OTLP partial success) is not sent again: those records are counted in heartbeat_otlp_export_rejected_records_total{client="audit"} and HeartbeatOTLPRecordsRejected fires. Without HEARTBEAT_API_AUDIT_ENDPOINT, nothing is sent and records wait; the chart sets it to the bundled OTel Collector's 4318 while the Collector is on, so in the minimal profile records wait. A round that finds records is traced: audit.drain → audit.export and the db.query of the delete.

Each record is an OTLP log record: severity INFO, the record's time, the record as compact JSON in the body (audit_record.schema.json), attributes event.name = heartbeat.audit and log.record.uid = the record's id, and the resource service.name = heartbeat-api with the replica's service.version, service.instance.id and deployment.environment.name. There is no service.namespace, so audit records stay out of Heartbeat's own logs (service_namespace="heartbeat"). The record's fields are id, time, request_id, actor (a user's user_id and email, a cli command and the host it ran on, or the address of a client that is not logged in), action, entity_type, entity_id, before, after and, for runtime config, config_version. In Grafana's Explore, on Loki:

{service_name="heartbeat-api"} | event_name="heartbeat.audit" | json | entity_type="user"

The logs themselves are in Loki with the labels service_namespace="heartbeat", service_name (db-collector, api) and deployment_environment_name:

{service_namespace="heartbeat", service_name="db-collector"} | detected_level="error"

Traces are in Tempo. A collection cycle is one trace, collector.cycle → collector.target → collector.probe → db.query or the outsystems.read, outsystems.build, outsystems.export, outsystems.derive and outsystems.watermark steps of a batch. An API request is <method> <route> → db.query and redis.<command>. /metrics and the health endpoints make none. A client's traceparent is linked, not continued. Spans name what ran, never query values, command arguments or error text, which can name a host and a login. A log line in a sampled span has its trace_id, and Grafana links the two ways; a line in a span that was not sampled has none, since Tempo never gets that trace.
